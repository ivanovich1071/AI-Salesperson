# Тесты — Playwright E2E

Полная картина и статус — в [TESTING.md](../../../TESTING.md) в корне проекта.
Здесь — рабочие правила для написания и починки тестов.

## Запуск

```bash
npm run test:e2e          # полный прогон + HTML-отчёт (≈5 мин, desktop + mobile)
npm run test:e2e:ui       # интерактивный режим, видно каждый шаг
npm run test:e2e:update   # обновить визуальные эталоны после правок дизайна
npm run test:report       # открыть последний отчёт
npx playwright test wizard --project=desktop --reporter=line   # один набор, быстро
```

Dev-сервер поднимать не нужно — `webServer` в конфиге делает это сам.
**Порт 3100 на время прогона занят**, локальный `npm run dev` работать не будет.

## Три вещи, которые ломают тесты, если о них забыть

**1. AI всегда мокается.** В каждом файле с визардом обязателен
`await mockAi(page)` в `beforeEach` — иначе тест пойдёт в живой OpenRouter
(8–30 сек, платно, каждый раз другой текст → «мигающие» падения).
Фикстуры и хелперы: `e2e/helpers/mockAi.ts`. При изменении формы ответа роута
обнови фикстуру — иначе мок разойдётся с продом и тест будет зелёным зря.

**2. Отдельная база.** `DATABASE_URL=file:./test.db` задаётся в `playwright.config.ts`,
схема и слоты создаются в `e2e/global-setup.ts`. Рабочую `prisma/dev.db` тесты
не трогают — иначе в админке появлялись бы фейковые заявки «ООО Тест».

**3. Визард помнит состояние.** Zustand persist в `localStorage`
(`ai-salesperson-wizard`). Каждый тест начинается с `openWizard(page)` — он открывает
`/app?new=1`, что сбрасывает стор. Без этого тесты «заражают» друг друга.

## Хелперы (`e2e/helpers/wizard.ts`)

Не пиши селекторы визарда заново — используй готовые:

- `openWizard(page)` — чистый старт
- `fillCompanyStep(page, {...})` — заполнить шаг 1 и перейти к анкете
- `answerFirstQuestion(page)` — отметить первый вариант
- `buildProposal(page)` — собрать предложение и дождаться шага 3
- `sendChat(page, text)` — отправить сообщение ассистенту
- `openChat(page)` — вернуть панель чата (на мобильном сама открывает нижний лист)
- `proposalBtnInForm(page)` / `proposalBtnInChat(page)` — кнопка «Сформировать
  предложение» есть в двух местах, всегда уточняй какая

## Типовые падения и причины

| Симптом | Причина | Решение |
|---|---|---|
| `strict mode violation: resolved to 2 elements` | одинаковый текст в двух местах (карточка и модалка, форма и чат) | сузить область: `page.locator("main")`, `page.locator("aside")`, `modal.getByRole(...)` |
| Таймаут на кнопке времени в брони | сначала надо выбрать **дату**, список времени появляется после | `main .grid button` → потом время |
| Не находится шаг степпера по номеру | пройденные шаги показывают «✓», а не цифру | искать по `button[title="Перейти: Диагностика"]` |
| Тест зелёный на десктопе, падает на мобильном | другое поведение: чат в нижнем листе, меню в бургере, карточки в столбик | `test.skip(({ isMobile }) => !!isMobile, "причина")` |
| Визуальный тест упал после правки дизайна | эталон устарел | посмотреть diff в отчёте, затем `npm run test:e2e:update` |

## Соглашения

- Названия тестов — по-русски, описывают пользовательский сценарий, а не реализацию:
  «стрелки СТОЯТ МЕЖДУ карточками», а не «process div has flex-row».
- Приоритет селекторов: роль и доступное имя (`getByRole`) → плейсхолдер → текст.
  CSS-классы — только когда иначе никак (модалки, декоративные обёртки).
- Проверяй **поведение**, а не разметку: не «есть класс `lg:flex-row`», а
  «стрелка правее карточки и на её высоте» — тогда тест переживёт рефакторинг стилей.
- Не добавляй `waitForTimeout` для «стабильности» — у Playwright авто-ожидание.
  Исключение: запись голоса, где нужна реальная длительность.
- Каждый новый пользовательский сценарий на странице — новый тест, а не ветка внутри
  существующего: так в отчёте видно, что именно сломалось.

## Что тесты не покрывают

Качество распознавания речи, осмысленность ответов AI и субъективную эстетику
автоматика не проверяет — это ручная приёмка.
