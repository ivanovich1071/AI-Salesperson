## 🔴 Приоритет 1 — сделать в первую очередь

### 1.1. Ограничение частоты запросов (rate limiting) — **защита от слива бюджета**

**Проблема, а не теория:** ни на одном из 11 API нет ограничений. Шесть роутов ходят в
OpenRouter за ваши деньги. Скрипт в 20 строк, дёргающий `/api/ai/chat` в цикле, за ночь
может выжечь весь баланс OpenRouter — при этом сайт формально «работает».

Дополнительно без ограничений открыты:
- `POST /api/diagnostics` — публичный, можно засыпать базу мусорными картами диагностики;
- `POST /api/bookings` — можно занять **все свободные слоты** Вероники ботом;
- `POST /api/transcribe` — приём файлов без лимита размера.

**Что делаем:** лимит по IP в middleware (например, 20 запросов/мин на `/api/ai/**`,
5/мин на `bookings` и `diagnostics`), плюс ограничение размера тела запроса.
Хранилище — в памяти процесса (сервер один, Redis разворачивать не нужно).

- [x] Лимиты на AI-роуты, брони, диагностику — [src/middleware.ts](src/middleware.ts)
- [x] Ограничение размера аудио в `/api/transcribe`
- [x] Понятный ответ 429 вместо технической ошибки

### 1.2. SSRF в `/api/parse-site` — **сервер ходит по любому адресу**

**Проблема:** роут принимает URL от пользователя и запрашивает его с сервера
([parse-site/route.ts:15-24](src/app/api/parse-site/route.ts)). Никакой проверки адреса нет.
Значит, через форму «Сайт компании» можно заставить ваш сервер сходить на
`http://127.0.0.1:3100/api/...`, во внутреннюю сеть хостера или к служебным адресам —
и вернуть содержимое в ответе. Это классическая уязвимость SSRF.

**Что делаем:** разрешать только `http/https`, резолвить хост и **блокировать приватные
диапазоны** (127.0.0.0/8, 10/8, 172.16/12, 192.168/16, 169.254/16, IPv6-локальные),
запретить редиректы на приватные адреса, поставить таймаут и лимит размера ответа.

- [ ] Белый список схем + чёрный список приватных диапазонов
- [ ] Таймаут, лимит размера, запрет опасных редиректов

### 1.3. Заголовки безопасности — сейчас их нет вообще

[next.config.mjs](next.config.mjs) пустой: нет ни одного защитного заголовка.
Сайт можно встроить в `<iframe>` на чужом ресурсе и обманом собирать клики
(кликджекинг), браузер не защищает от подмены типов содержимого.

- [ ] `X-Frame-Options: DENY` (или `frame-ancestors 'none'`)
- [ ] `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`
- [ ] `Strict-Transport-Security` (HTTPS уже есть — включить принудительно)
- [ ] `Content-Security-Policy` — аккуратно, начиная с `report-only`

### 1.4. Домен вместо `nip.io` — **без этого SEO не существует**

Сейчас сайт живёт на `https://81-177-214-84.nip.io`. Это сервис-заглушка, который
резолвит IP в имя. Для поисковиков это не бренд, а технический адрес: такой сайт
практически не ранжируется, ссылку неловко давать клиентам, а в мессенджерах она
выглядит подозрительно.

**Что делаем:** купить домен (например, `vibemind.by` / `vibemind.pro`), направить на
`81.177.214.84`, выпустить сертификат Let's Encrypt (в [DEPLOY.md](DEPLOY.md) уже описано
как), настроить редирект со старого адреса.

- [ ] Домен куплен и делегирован **(решение и оплата — за вами)**
- [ ] Сертификат, редирект `nip.io` → домен (301)
- [ ] Обновить `NEXT_PUBLIC_SITE_URL` и метатеги

## 🟡 Приоритет 3 — производительность и UX

### 3.1. Изображения — главный тормоз загрузки

`PVN-v1.jpg` весит **405 КБ**, логотипы — по **450 КБ**, используются обычные `<img>`
без ленивой загрузки и без указания размеров. Это напрямую бьёт по Core Web Vitals
(LCP и CLS), а они входят в факторы ранжирования.

- [ ] Перевести на `next/image` (авто-WebP, ленивая загрузка, нужные размеры)
- [ ] Пережать исходники: цель — до 100 КБ на изображение
- [ ] Указать `width`/`height`, чтобы страница не «прыгала» при загрузке

### 3.2. Пользовательские сценарии визарда

- [ ] **Стриминг ответа AI** — сейчас чат молчит 8–30 секунд, видно только «печатает».
      Постепенный вывод ответа снимает ощущение зависания.
- [ ] **Контраст кнопок** — 3.04 при норме 4.5 (см. [TESTING.md](TESTING.md)).
      Ждёт вашего решения: затемнить до `#0f7679` или оставить.
- [ ] **Чат на мобильном** — нижний лист перекрывает форму; нужен автоскролл к активному
      полю (это же чинит 4 нестабильных теста).
- [ ] **Восстановление после ошибки** — если AI не ответил, дать кнопку «Повторить»
      вместо предложения начать заново.
- [ ] **Прогресс диагностики** — показывать «отвечено 3 из 7», чтобы было видно, сколько
      осталось.
- [ ] **Страница 404** в фирменном стиле с возвратом на главную.

### 3.3. Надёжность

- [ ] Автобэкап `prod.db` (SQLite) по расписанию — сейчас брони существуют в одном
      экземпляре на сервере
- [ ] Sentry или аналог: сейчас об ошибке у клиента вы узнаете только от клиента
- [ ] Прогон E2E-тестов встроить в `scripts/deploy.sh` перед пушем

## Порядок работ

| Этап | Что | Ориентир |
|---|---|---|
| 1 | Rate limiting + SSRF + заголовки безопасности | 1 подход |
| 2 | Домен, HTTPS, редиректы | ваше решение + 1 подход |
| 3 | robots/sitemap/OG/JSON-LD/метрика | 1 подход |

Этапы 1 и 3–5 можно делать без вас. **Этап 2 упирается в покупку домена** — это
единственное, что требует вашего действия и оплаты.

## Что НЕ предлагаю и почему

Чтобы не раздувать проект ради галочек:

- **Переход на PostgreSQL** — SQLite для текущих объёмов (десятки заявок) достаточно.
  Менять при росте нагрузки, а не «на будущее».
- **Docker/Kubernetes** — деплой в одну команду уже работает, контейнеры добавят
  сложности без выгоды на одном сервере.
- **Отдельный CDN** — статики мало, nginx справляется. Сначала сжать картинки.
- **Полноценный CMS** — пока контент меняется раз в неделю, править код быстрее.
